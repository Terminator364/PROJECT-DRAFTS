# README — Méthode universelle de production des projets
Version 1.0 — 2026-11-26 — décision propriétaire : GitHub comme fil conducteur, priorité au gratuit, continuité inter-conversations.
Ce document complète AGENTS.md et CI_BUDGET_POLICY.json ; il ne révoque ni les protections de production ni les exceptions CI spécifiques existantes.

## 1. Entrée obligatoire pour chaque conversation ou agent
Dès qu'une demande concerne un projet technique (création, reprise, correction, audit, mise à jour, installation, migration), identifier le projet et lire cette procédure depuis la branche par défaut de PROJECT-DRAFTS. Lire ensuite AGENTS.md, CI_BUDGET_POLICY.json, NEW_PROJECT_BOOTSTRAP.md, puis README.md, DIRECTION.md et les sections pertinentes de MEMOIRE_MAITRE.md du projet réel, sur sa branche de travail. Examiner les PR, commits, versions, incidents et tâches déjà ouverts avant toute mutation. Retrouver les décisions anciennes dans les sources autorisées ; ne pas demander à nouveau ce qui est déjà documenté. Si une source est inaccessible, identifier la lacune et avancer sur le périmètre indépendant ; ne pas inventer son contenu.

## 2. Choix du dépôt et autorité
- Projet nouveau sans dépôt : sous-dossier clairement nommé dans PROJECT-DRAFTS, branche isolée, contenu non confidentiel uniquement.
- Projet existant : reprendre son dépôt et sa branche réels, ne pas créer un doublon. À maturité, dépôt privé dédié ou branche/sous-dossier privé dans un dépôt existant si le propriétaire le décide. Respecter les frontières entre projets.
- GitHub est l'autorité de développement : sources, architecture, décisions, tests, versions, historique et préparation des releases. Le PC est une cible d'exécution, de validation matérielle et de déploiement, pas un deuxième dépôt de développement permanent. ChatGPT orchestre ; Drive et les autres supports ne deviennent pas des autorités concurrentes du code.
- Les règles particulières de données opérationnelles restent en vigueur (par exemple Drive comme vérité runtime externe de ChatGPT-PC) jusqu'à décision explicite de les changer. Ne pas supprimer la télémétrie nécessaire ni les backups indispensables.
- Choix explicites du propriétaire priment sur les décisions de classement proposées par l'agent. Pas de modification de visibilité d'un dépôt sans accord.

## 3. Architecture et continuité
Un seul README stable (constitution, méthode, limites), une seule DIRECTION (état réel, versions installées/candidates, risques, prochain travail), une seule MEMOIRE_MAITRE (historique cumulatif, décisions, preuves, incidents, leçons et lacunes). Pour les projets qui adoptent les huit familles, conserver ARCHITECTURE, GOUVERNANCE, SYSTEME, MODULES, OUTILS, MEMOIRE, ARCHIVES, PROJETS ; respecter l'architecture propre d'un projet existant et ne pas l'écraser pour imposer le modèle. Dossiers modules séparés : ACTUEL, LAB, DESIGN, RELEASES, HISTORIQUE, VALIDATION selon besoin.
Chaque tâche dispose d'un identifiant, d'une base/version, d'objectifs vérifiables, d'un état et d'une preuve. Avant sortie : mettre à jour DIRECTION et MEMOIRE_MAITRE, pointer les commits/PR/tests, décrire écarts et prochaine action. Ne pas effacer les preuves historiques ni inventer des messages ou des commits anciens. Les exports verbatim ne sont conservés que s'ils sont accessibles et autorisés, dans un espace privé adéquat.

## 4. Production GitHub-first
B0 inventaire et réconciliation de la version réellement installée ; B1 exigences et critères ; B2 conception (validation UI humaine si pertinente) ; B3 architecture et menaces ; B4 candidat isolé sur branche ; B5 tests unitaires, intégration, erreurs et non-régression ; B6 validation système et restauration ; B7 promotion réversible après les autorisations applicables.
Grouper les modifications cohérentes. Ne pas recompiler une version ancienne en écrasant des améliorations récentes. Garder la base immuable ; versionner les candidats et les preuves. Les branches/PR de travail ne sont pas une installation. Ne pas fusionner, publier, signer ou déployer prématurément. Un GO de préparation ne vaut pas GO de déploiement. Une autorisation locale requise par l'outil doit être respectée.

## 5. Circuit privé/public, ressources gratuites en priorité
ChatGPT-PC (privé) ou le dépôt privé propre au projet = source complète. PROJECT-DRAFTS (public) = laboratoire de composants indépendants explicitement admissibles à la publication : code non confidentiel revu, fixtures synthétiques, tests, builds non sensibles.
Précédents : PROJECT-DRAFTS PR #17 OneClick (20 fichiers autonomes revus, manifeste), PR #48 PCRC V2 (laboratoire public isolé), PR #13 BookHarvester (qualification Windows puis déclenchement manuel). Utiliser ces modèles sans les copier aveuglément.
Étapes : inventaire et classification ; revue des secrets et données ; liste positive des fichiers publiables ; transfert des seuls composants approuvés ; correspondance SHA Git source/tests ; tests publics ; retour des preuves et correctifs dans la branche privée ; tests d'intégration privés et terrain. Aucun checkout privé, token privé, donnée personnelle, journal HP, clé de signature ou archive confidentielle dans le public. Les secrets d'accès ne vont pas dans Git, même privé. La CI publique ne certifie que son périmètre testé. Aucun contournement de quota, aucune multiplication artificielle de comptes ou runners.

## 6. Budget CI
Zéro dépense par défaut, zéro minute GitHub-hosted privée en routine ; conserver la politique budgétaire canonique (objectif global historique 30 minutes privées/planifiées par mois, allocations non assimilables à des autorisations). Priorité aux ressources gratuites légitimes ; vérifier l'éligibilité actuelle des runners publics standards et les limites de stockage/usage avant lancement. Pas de runner payant, workflow automatique push/PR/schedule sans autorisation explicite, ni boucle de relances identiques. Préférer validation statique/locale peu coûteuse, puis un workflow manuel ciblé, timeout borné, permissions contents:read, credentials non persistants, rétention minimale, annulation des exécutions devenues obsolètes. Les exceptions nommées existantes restent limitées à leur périmètre ; un nouveau laboratoire public nécessite revue et décision de périmètre, sans autoriser une dépense. Ne pas présenter un build public comme un release privé signé.

## 7. Migration et nettoyage
Inventorier origines PC/Drive/GitHub/ChatGPT accessibles, noms indirects, anciennes archives, exports, dépendances, jonctions, fichiers binaires et sources. Classifier par version et sensibilité ; établir manifeste tailles, SHA-256, provenance, exclusions, lacunes. Transférer vers destination adaptée et relire ; comparer empreintes des octets originaux, pas seulement une transcription texte ou un nom de fichier ; tester restauration sur un espace isolé. Conserver les versions réellement retrouvées sans fabriquer leur filiation. Seules les copies obsolètes et précisément identifiées peuvent être supprimées après preuve de restauration et autorisation de nettoyage applicable. Ne pas supprimer la version installée, les données nécessaires, les documents mixtes d'autres projets ni les éléments hors portée. Ne pas prétendre effacer des chats, fichiers ou comptes inaccessibles.

## 8. Validation et qualité
Mesurer sur matériel et version réels, selon le périmètre : test nominal, erreurs, redémarrage, coupures réseau/énergie, reprise, rollback, compatibilité, ressources CPU/RAM, UX, sécurité, données incohérentes et tests historiques hors apprentissage. Définir PASS/FAIL/PARTIAL/BLOCKED par critère ; distinguer commande acceptée, code de sortie, effet réellement vérifié, résultat terrain. Un outil indisponible n'est pas une preuve de réussite ou d'échec du système. Préserver la dernière version connue fonctionnelle et un retour arrière vérifié. Ne pas dégrader une interface ou fonctionnalité non visée.

## 9. Collaboration
Agir sur les décisions déjà prises, sans répéter des questions résolues. Demander seulement les arbitrages réellement nécessaires, permissions effectives ou décisions irréversibles non autorisées. Communiquer résultats vérifiés et bloqueurs, pas de promesse de travail entre conversations sans mécanisme réel. Si le propriétaire demande de continuer, reprendre au dernier jalon ouvert, ne pas recommencer. Un rapport doit préciser ce qui a changé, où, les preuves, les limites, décisions prises par défaut et ce qui reste à faire. Une tâche terminée exige preuve de résultat ; le silence ou une compilation seule ne valent pas PASS.

## 11. Adoption et limites
Référence unique de cette méthode : PROJECT-DRAFTS, branche par défaut, README_PRODUCTION_UNIVERSELLE.md. Les README/AGENTS des autres dépôts pointent vers elle ; ne pas maintenir de versions divergentes de cette procédure. Les agents doivent pouvoir lire GitHub et suivre ces instructions ; aucun README ne déclenche automatiquement ChatGPT dans toutes les conversations, ne donne des permissions supplémentaires ou ne garantit une lecture quand GitHub est inaccessible.
